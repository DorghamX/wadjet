- **T4.7 — `/admin` is a 303 to its Users tab.** The brief says decide what `/admin` itself renders and log it. After comparing against the design's expectations (the top‑bar `Admin` link, the tabs row already shows Users / Groups / Permissions, no separate index page was needed), the choice was to make `/admin` a redirect to `/admin/users` with status 303. This keeps a single canonical home and avoids keeping an index page in sync with the three tab views. The decision is logged here so Track B can resolve the merge conflict if `/admin` ever needs its own page.

- **T4.7 — Admin users, groups, and the permission matrix.** Three new endpoints were built: `GET/POST/PATCH /api/v1/users` and `/api/v1/groups` (admin session only, validated with Pydantic, 409 on taken names, 422 on empty body, `users.admin` permission enforced). The service functions live in `app/api/users.py` and are shared with the pages at `app/web/admin.py`. Three HTML templates were added: `admin_users.html`, `admin_groups.html`, `admin_permissions.html` using a shared `admin_shell.html` and the design's copy style. The matrix reads `PERMISSION_TEMPLATES` from `app/permissions.py` and lists every permission from section 7 with its "allows" text. No new database tables were needed beyond `users`, `groups` and `group_members` which already exist from T1.2. A new `users` API module and a new `admin` pages module were created; existing read‑only interfaces (`can()`, `PERMISSION_TEMPLATES`, `write_audit()`, `read_audit()`) were not touched. The `/me` route already existed at `GET /api/v1/me` (section 14), so nothing changed there.
